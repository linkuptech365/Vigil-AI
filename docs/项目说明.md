# Vigil-AI 项目说明

Vigil-AI（OmniVision Sentinel）是一个面向生物医药洁净室等受监管场景的视频智能预警平台。它把“边缘初筛、大模型复核、规则防抖、处置联动、证据归档”串成一条完整链路，目标是只把真正值得人工关注的事件送到值班人员面前，并且每一次告警都有可校验的证据。

本文档基于当前代码整理，内容分为：项目定位、技术架构、功能清单、核心业务流程、数据与存储、接口清单、配置与部署、已知限制。

---

## 1. 项目定位

| 项目 | 说明 |
| --- | --- |
| 目标用户 | 洁净室、车间、仓储等需要持续合规稽查的现场与质量管理人员 |
| 核心问题 | 摄像头多、画面长，人工盯屏成本高；纯大模型逐帧研判成本高、误报多 |
| 解决思路 | 分层过滤：低成本的一级检测先筛掉绝大多数画面，仅疑似画面才交给大模型二级研判 |
| 交付结果 | 告警流、自动建案、证据封存与完整性校验、联动通知、人工处置闭环 |

## 2. 技术架构

### 2.1 技术栈

| 层 | 技术 |
| --- | --- |
| 前端与网关 | Next.js 16（App Router）、React 19、TypeScript、Tailwind CSS 4、shadcn/ui（Radix）、SWR |
| 视频播放 | hls.js、WHEP/直连回退、MJPEG 与快照接口 |
| 流媒体网关 | go2rtc（`bin/go2rtc`，由 `lib/stream-engine.ts` 托管启动、注册与注销通道） |
| 抽帧 | ffmpeg-static |
| 一级视觉服务 | Python FastAPI（`services/vision-worker/main.py`），YOLO 开放词表检测 + 跟踪（ByteTrack 适配，缺失时回退 IoU 跟踪） |
| 二级研判 | 可配置的多模态大模型网关（OpenAI 兼容、Ollama、Gemini 等），不可用时使用离线启发式兜底 |
| 证据包 | jszip + Web Crypto（浏览器端 SHA-256） |
| 部署 | Docker 三阶段镜像、docker-compose、Next.js standalone 输出 |

### 2.2 进程与职责

服务启动时由 `instrumentation.ts` 在 Node 运行时拉起三件事（均不阻塞启动）：

1. `ensureEngine()`：启动并维护 go2rtc 流媒体网关。
2. `ensureVisionEngine()`：启动并健康检查 Python 视觉服务，崩溃自动退避重启，并把配置与围栏下发给它。
3. `startStreamPatrol()`：启动自动巡检定时器（每 15 秒检查一次，每路通道至少间隔 60 秒）。

```
浏览器（/ 作业大屏、/console 配置中心）
        │  HTTP / SSE
        ▼
Next.js 网关（app/api/v1/*）
   ├─ lib/stream-engine.ts ── go2rtc ── 摄像头 / 本地视频
   ├─ lib/vision-engine.ts ── Python vision-worker（一级检测、跟踪、围栏）
   ├─ lib/stream-patrol.ts ── 定时巡检（视觉服务不可用时的兜底）
   ├─ lib/ops/server/stream-analysis.ts ── 二级研判编排
   ├─ lib/ops/server/vlm-engine.ts ── 大模型调用 / 离线兜底
   ├─ lib/ops/server/rule-engine.ts ── 规则、冷却防抖、聚类
   ├─ lib/ops/server/alert-linkage.ts ── 联动渠道
   └─ lib/storage/*.ts ── data/ 目录下的 JSON 与证据文件
```

## 3. 页面与功能清单

### 3.1 作业大屏 `/`（`components/ops/ops-center.tsx`）

| --- | --- | --- |

| 一级感知初筛 | `perception/*`、`vision-card` | 一级检测指标、电子围栏绘制与管理、检测词表与一级规则录入、升级队列 |
| 二级多模态研判 | `vlm/*` | 对本地视频或通道关键帧执行大模型研判，展示因果推理链、证据帧、Video-RAG 检索 |
| 规则与防抖引擎 | `rules/*` | 规则库增删改、自定义语义规则、冷却窗口可视化、告警风暴模拟、跨机位事件聚类 |
| 处置联动与证据归档 | `dispatch/*`、`audit/*` | 真实告警案卷、处置状态流转、联动渠道结果、证据完整性校验与证据包导出、误报反馈 |

### 3.2 配置中心 `/console`（`components/vigil/vigil-app.tsx`）

| 标签页 | 功能 |
| --- | --- |
| 配置 | 模型网关档案（多模型、服务端保存密钥）、视频流管理、一级检测配置与词表编译、灵敏度预设、演示数据开关 |
| 实时监控 | 实时墙、AI 标注画面、视觉漏斗统计、引擎状态横幅 |
| 检测队列 | 扫描目录中的视频、抽帧、研判、GMP 基准算例一键注入、队列与终端日志 |
| 预警中心 | 研判产生的告警列表与实时流告警区（`stream-alerts-section`） |

### 3.3 能力分项

**接入层**
- 视频流注册与注销，内置演示循环流，通道区域（zone）命名。
- 目录扫描与视频元数据读取，路径白名单与符号链接校验（`path-guard.ts`、`url-guard.ts`）。
- 本地视频统一切片，供接入、一级、二级共用。

**一级感知初筛**
- 开放词表检测：词表条目由“中文名、英文提示词、角色”组成，角色分为主体锚点、必需劳保、违规目标。
- 词表可手动增删改、可用中文描述由大模型编译成英文词表，编译结果追加合并到现有词表（按英文词去重、保留手动编辑），上限仅作异常保护（300）。
- 三阶门控：运动检测（Tier-0）、目标判定（Tier-1）、连续帧确认加冷却。
- 电子围栏：多边形区域与绊线，可在实时画面上直接绘制，保存后热更新到视觉服务；围栏判定目前只针对人员目标，动作为“仅记录”的围栏不触发送审。
- 视觉服务不可用时，降级为 Node 端帧差预筛，保证链路不断。

**二级多模态研判**
- 按“通道绑定的规则”组装提示词，抽取多帧送大模型，输出结论摘要、严重等级、置信度、因果推理链、证据帧。
- 灵敏度阈值：命中规则但置信度低于阈值，不告警，只记录原因。
- 大模型不可用、未配置密钥或端点指向自身时，自动走离线兜底，并在结果中标明来源。

**规则与防抖**
- 规则库由服务端持有（`data/rules.json`），支持内置规则、GMP 洁净室预设、自定义语义规则。
- 规则可绑定“全部视频源 / 本地视频 / 指定通道”，可设置严重等级、灵敏度、冷却窗口、生效时段。
- 冷却窗口内同通道同规则的重复触发折叠进既有事件。
- 跨机位按时间、语义、拓扑计算亲和度，把多路告警聚类为一张工单。

**处置与归档**
- 告警落库即封存证据、自���建案、自动联动。
- 案卷状态：待处置、已确认、已派工、处置中、已结案、误报；每次操作都写入案卷动作日志。
- 证据包导出（ZIP，含清单与逐文件 SHA-256），可随时校验证据文件是否被改动。
- 误报需选择原因并填写说明，形成反馈记录。

## 4. 核心业务流程

### 4.1 总览

```
摄像头 / 本地视频
   │ go2rtc 拉流
   ▼
[一级] Python vision-worker 按 sampleFps 抽帧
   ├─ Tier-0 运动检测：画面静止且无待复核目标 → 直接过滤
   ├─ Tier-1 开放词表检测 + 跟踪 + 围栏判定 → 得到“疑似目标”
   ├─ 连续命中 minConsecutiveFrames 帧 → 才确认疑似
   └─ 冷却 cooldownSeconds → 同一目标不重复送审
   │ POST /api/v1/incident/trigger（携带 4 帧原图 + 1 帧标注图）
   ▼
[二级] analyzeStream：规则组装 → 大模型研判（或离线兜底）
   ├─ 未命中 / 低于灵敏度 / 被冷却折叠 → 只写研判记录，不出告警
   └─ 命中且未被折叠 → 生成告警
          │
          ├─ saveAlert：写入关键帧 → 逐文件 SHA-256 → 写 manifest.json → 自动建案
          ├─ fireAutoLinkage：Webhook、IM 机器人，严重（CRITICAL）时再触发声光与 IoT
          └─ recordAnalysis / appendRecord：写研判记录
   ▼
[展示] 右侧 AI 研判告警流、处置联动页案卷、证据完整性校验
```

### 4.2 一级到二级的触发条件

一级在视觉服务内完成，判定规则（`main.py` 的 `evaluate()`）：

1. 只认置信度不低于 `confidenceLow`（默认 0.4）的检测框。
2. 人员缺少必需劳保，或违规目标与人重叠，或画面中单独出现违规目标，均记为疑似；全部合规但置信度处于 `confidenceLow` 与 `confidenceHigh`（默认 0.85）之间时，按模糊区间疑似处理。
3. 同一目标连续命中 `minConsecutiveFrames`（默认 3）帧才触发；围栏类疑似为即时触发。
4. 触发后进入 `cooldownSeconds`（默认 30 秒）冷却。
5. 触发时向 `/api/v1/incident/trigger` 送审，若配置了 `VIGIL_EDGE_TOKEN` 则需 Bearer 鉴权。

检测时模型最低阈值取 `min(0.25, confidenceLow)`，所以标注画面会画出低于 0.4 的框，但这些框不会进入告警判定。

### 4.3 二级研判的结局

每次研判（含失败）都会写入一条研判记录（`stream-records.json`），结局类型：

| 结局 | 含义 |
| --- | --- |
| alert | 命中规则且未被折叠，已生成告警 |
| folded | 命中规则，但在冷却窗口内，折叠进既有事件 |
| safe | 大模型复核后无违规，或命中但低于规则灵敏度阈值 |
| error | 抓帧失败、模型未就绪、无生效规则等 |

边缘送审被驳回且边缘置信度不低于 0.8 的样本会标记为“难例（hardSample）”，用于后续复盘。

### 4.4 自动巡检的分工

- 视觉服务就绪且在监控的通道：由视觉漏斗接管，只有疑似才触发大模型。
- 视觉服务不可用的通道：由定时巡检兜底，每 60 秒一次，先用 Node 端帧差判断自上次研判以来画面是否变化，没变化不送审。
- 通道需开启 `autoPatrol` 才会参与自动巡检。

### 4.5 告警落库、建案与证据封存

`saveAlert` 一次完成：

1. 关键帧写入 `data/stream-evidence/<alertId>/N.jpg`。
2. 逐文件计算 SHA-256，写入 `manifest.json`（格式 `vigil-evidence/1`）。
3. 计算研判事实部分的记录哈希（不含处置过程与封存信息，处置动作不会使它失效）。
4. 自动建案，案号 `CASE-YYYYMMDD-NNN`，状态“待处置”，写入第一条系统动作。
5. 清理超过保留期的证据（默认 365 天，可用 `VIGIL_EVIDENCE_RETENTION_DAYS` 调整）。

校验接口 `verifyEvidence` 会重新计算文件哈希与记录哈希，对比封存值，任何改动都能发现。

### 4.6 联动渠道

| 渠道 | 环境变量 | 触发条件 |
| --- | --- | --- |
| 业务系统 Webhook | `VIGIL_LINKAGE_WEBHOOK_URL` | 每次告警 |
| IM 机器人（飞书、钉钉、企微） | `VIGIL_LINKAGE_IM_URL` | 每次告警 |
| 现场声光警号 | `VIGIL_LINKAGE_SIREN_URL` | 仅 CRITICAL 自动触发，人工“全渠道广播”可强制触发 |
| IoT 闸机、门禁联锁 | `VIGIL_LINKAGE_IOT_URL` | 仅 CRITICAL 自动触发，人工可强制触发 |

未配置地址的渠道如实记为 `NOT_CONFIGURED`，不会伪装成已送达；结果与动作都写回案卷。

### 4.7 人工处置闭环

案卷状态流转：待处置 → 已确认 → 已派工 → 处置中 → 已结案；任意阶段可标记误报（需填写原因与说明）。每个动作记录操作人、时间、类型、备注。处置页可查看关键帧胶片、证据哈希卡片、联动结果、案卷动作时间线，并导出证据包。

### 4.8 词表逐步完善流程

1. 在“一级感知初筛”或配置中心的一级检测卡片中，用中文描述稽查要求。
2. 点击“编译并热更新”，大模型把描述翻译成英文检测词条。
3. 新词条追加合并到现有词表：按英文词去重，已有启用的主体锚点时不重复添加，已停用的同名词条会被重新启用，手动编辑全部保留。
4. 保存后热更新到视觉服务，无需重启。
5. 也可以手动“添加词条”，逐条调整中文名、英文词、角色与启停。

## 5. 数据与存储

全部为本地文件，目录由 `VIGIL_DATA_DIR` 决定，默认 `<项目>/data`，Docker 内为 `/app/data`（命名卷持久化）。写入采用临时文件加重命名的原子方式。

| 文件 | 内容 |
| --- | --- |
| `rules.json` | 稽查规则库 |
| `models.json` | 模型网关档案（含密钥，文件权限 600，接口只返回掩码） |
| `streams.json` | 视频流清单与自动巡检开关 |
| `roi-zones.json` | 电子围栏与绊线 |
| `vision-config.json` | 一级检测配置与词表 |
| `stream-alerts.json` | 告警、案卷、封存信息 |
| `stream-evidence/<alertId>/` | 关键帧图片与 `manifest.json` |
| `stream-records.json` | 每次研判的记录（含失败与折叠） |
| `demo-mode.json` | 演示数据开关，默认关闭 |
| `go2rtc.yaml` | 流媒体网关配置，由程序自动生成，不要手工编辑 |

演示数据默认关闭，只有在设置中主动开启才会展示模拟数据。

## 6. 接口清单（`/api/v1`）

**基础与连通**
`GET /health`、`POST /test-connection`、`GET/POST /settings/demo`

**视频与抽帧**
`POST /scan-folder`、`POST /extract-frames`、`GET /videos/stream`、`POST /samples/provision`

**视频流与通道**
`GET/POST /streams`、`GET/PATCH/DELETE /streams/{id}`、`POST /streams/{id}/analyze`、`/test`、`/inspect`，`GET /streams/{id}/snapshot`、`/mjpeg`、`/annotated`，`/streams/engine`

**一级视觉**
`GET/PUT /vision/config`（仅引擎运行参数，不含词表）、`GET /vision/engine`、`GET/PUT /roi-zones`；检测词表仅通过各通道的 `channel-perception` 接口编译与维护

**二级研判**
`POST /vlm/analyze`（SSE）、`POST /incident/trigger`（边缘送审入口）

**规则引擎**
`GET/POST /rules`、`PATCH/DELETE /rules/{id}`、`POST /rules/evaluate`、`GET/POST /rules/suppress`、`POST /rules/simulate-storm`、`GET/POST /rules/cluster`、`POST /rules/reset`、`POST /rules/preset/gmp`

**模型网关**
`GET/POST /models`、`PATCH/DELETE /models/{id}`、`POST /models/{id}/default`

**告警与处置**
`GET /stream-alerts`、`GET/PATCH /stream-alerts/{alertId}`、`/stream-alerts/{alertId}/archive`（证据封存校验与导出）、`/stream-alerts/{alertId}/frames/{index}`

所有携带物理路径的接口都会拒绝空字节与 `..` 跳转，并在解析符号链接后校验路径落在白名单内。

## 7. 配置与部署

### 7.1 环境变量

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `PORT` | 3000 | 网关端口 |
| `VIGIL_DATA_DIR` | `<cwd>/data` | 持久化目录 |
| `VIGIL_ALLOWED_ROOTS` | 空 | 追加授权的视频目录白名单，Linux 以 `:` 分隔 |
| `VIGIL_SCAN_DIR` | 空 | 按文件名寻址视频时额外查找的目录 |
| `VIGIL_EDGE_TOKEN` | 空 | 边缘送审的 Bearer 凭证，视觉服务与网关共用 |
| `VIGIL_INTERNAL_URL` | `http://127.0.0.1:<PORT>` | 视觉服务回调网关的地址 |
| `VIGIL_VISION_PORT` | 1985 | 视觉服务端口 |
| `VIGIL_DISABLE_VISION_ENGINE` | 空 | 禁用视觉服务，改用 Node 端兜底 |
| `VIGIL_DISABLE_STREAM_ENGINE` | 空 | 禁用 go2rtc |
| `VIGIL_PYTHON_HOME`、`VIGIL_PYTHON`、`VIGIL_USE_UV` 等 | 空 | Python 运行环境选择与一键安装控制 |
| `VIGIL_MODELS_DIR` | `<项目>/models` | 一级检测权重目录 |
| `VIGIL_EVIDENCE_RETENTION_DAYS` | 365 | 证据保留天数 |
| `VIGIL_LINKAGE_WEBHOOK_URL`、`_IM_URL`、`_SIREN_URL`、`_IOT_URL` | 空 | 联动渠道对端地址 |
| `NEXT_PUBLIC_DEFAULT_VLM_MODEL` | `qwen2.5-vl-72b` | 默认二级研判模型标识 |

- 配置并启用至少一个模型网关档案，并设为默认。
- 设置 `VIGIL_EDGE_TOKEN`，避免任何人伪造边缘送审。
- 为需要自动巡检的通道开启 `autoPatrol`，并在规则库中把规则绑定到“全部视频源”或对应通道，否则二级研判会返回“没有生效的稽查规则”。
- 按需配置联动渠道地址。
- 数据全部落在本地文件系统，部署到只读或临时文件系统的环境前，需要先挂载持久卷。

## 8. 已知限制与注意事项

1. **标注画面与告警门槛不一致**：AI 标注层会画出置信度 0.25 以上的框，但只有不低于 `confidenceLow` 的目标才进入告警判定，所以会出现“有框没告警”。这是当前设计行为，尚未统一口径。
2. **规则库与一级词表是两套数据**：规则库中的自定义语义规则只影响二级大模型提示词；一级是否检测某类目标由检测词表决定。例如规则写了“人或猫吃东西”，如果一级词表里没有对应词条，一级不会送审。
3. **围栏只对人员生效**：当前下发给视觉服务的围栏仅包含目标类型含“人员”且动作不是“仅记录”的围栏。
4. **视觉服务依赖 PyTorch 与权重**：未安装时进入降级模式，只做运动检测，不产生检测框，也不会产生一级送审。
5. **二级被驳回只记研判记录**：被大模型判定为不成立的送审不会生成告警，可在研判记录中查看原因。
6. **冷却有两层**：一级对同一目标有 `cooldownSeconds`，规则库对同通道同规则有 `cooldownSeconds`，两者独立生效。
7. **证据与数据存放在本地文件**：没有数据库，备份与迁移需要同步整个数据目录。
8. **联动渠道未配置时不会送达**：处置页会如实显示“未配置”，不是故障。
